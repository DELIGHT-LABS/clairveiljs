# ClairveilJS Errors and Recovery Guide

## Purpose and principles

This document explains how to classify failures from ClairveilJS calls and decide whether a transaction may be retried or whether reservations and on-chain state must be reconciled first.

The most important rule is:

> If a transaction may have reached the network even once, reconcile the existing transaction identity, nullifiers, and output evidence before creating or resubmitting a new transaction.

- Store initialization, restart, and key rotation: [Storage and persistence](./storage-and-persistence.md)
- Reservation states and evidence guards: [Note Reservation State Transitions](./reservation-state-machine.md)
- External endpoints and success criteria: [API mapping](./api-mapping.md)

## Four forms of failure

ClairveilJS failures do not appear in only one exception format.

| Form | Example | Handling rule |
| --- | --- | --- |
| `ClairveilError` throw | planner, prover, operation consistency | Branch on `isClairveilError(error)` and `error.code`; use `details` for diagnosis. |
| Generic `Error` throw | profile validation, endpoint/response shape, wallet/network mismatch, reservation guard | The message is diagnostic. Do not use the entire string as a long-term program contract. |
| Result object | planner `status`, `ok`, `error`, or `errors` from some broadcast/wait APIs | Do not treat a resolved Promise as success; inspect the explicit status. |
| Reservation/operation state | `Unknown`, `ManualReview`, `ConfirmedSpent`, `ConflictSpent` | Read the current durable state and follow the evidence rules in the state-transition document. This state, rather than the original exception, is the basis for reuse safety. |

The `code` returned by an external wallet/provider is not in the same namespace as `ClairveilErrorCode`. For example, EIP-1193 user rejection `4001` is a provider code; it may be rethrown as the original error rather than converted to the SDK's stable error code.

## Using `ClairveilError`

```js
import {
  ClairveilErrorCode,
  isClairveilError
} from "clairveiljs/errors";

try {
  await runPrivacyOperation();
} catch (error) {
  if (isClairveilError(error, ClairveilErrorCode.PROVER_TIMEOUT)) {
    // Check the current reservation state and broadcast evidence before recovery.
  } else {
    throw error;
  }
}
```

The common `ClairveilError` fields are `code`, `message`, and `details`. When possible, prover errors also expose `status`, `proverCode`, and `retryable`. `details.cause` may contain the original error or sensitive request information, so do not serialize it directly into user messages or remote logs.

## Stable error codes currently produced

The following codes are currently generated by the SDK as `ClairveilError` contracts.

| Code | Condition | Recommended handling |
| --- | --- | --- |
| `INVALID_ARGUMENT` | Unsupported wallet type or an uncategorized planner failure | Fix the input and active profile, then prepare again from the beginning. |
| `INVALID_AMOUNT` | Amount is zero or negative, or the amount plan is invalid | Fix the user input. |
| `INSUFFICIENT_BALANCE` | The sum of verified spendable notes is insufficient | Deposit/receive funds or refresh the scan, then create a new plan. |
| `SELF_MERGE_REQUIRED` | A self-merge is needed first because of input limits | Perform the separate self-merge using the action and next amount in `error.details.plan`. |
| `ZERO_DUMMY_REQUIRED` | The transfer shape requires a zero-value helper note | Create the helper note, then create a new plan. |
| `EXACT_NOTE_REQUIRED` | Withdraw requires one exactly matching note | Create an exact note with a shielded self-transfer, then plan again. |
| `PROVER_UNAVAILABLE` | No prover URL, or a retryable HTTP/network failure | Check the endpoint. Confirm that the reservation is in a safe pre-broadcast state before retrying from the same checkpoint. |
| `PROVER_TIMEOUT` | Prover request or async job timed out/was aborted | Determine whether the adapter may complete later and query it using the checkpoint/job ID. Do not blindly request a duplicate proof. |
| `PROVER_CANCELLED` | Client prover wait or async job polling was cancelled | This only means the client wait ended; it does not guarantee that an in-process solver stopped. A general prepare helper may roll a valid `Proving` lease back to `Released`, so reread the current durable state and track the job/checkpoint in a separate operation store. Do not infer server-side cancellation or proof disposal from `Released` alone. |
| `PROVER_REJECTED` | Non-retryable prover response or proof job failure | Investigate payload/circuit/config mismatches. Do not blindly retry the same inputs. |
| `OPERATION_STATE_MIXED` | Linked reservations in one operation have different states | Inspect `details.reservations` and isolate/reconcile the entire operation. |
| `OPERATION_EVIDENCE_CONFLICT` | Transaction/output/disclosure evidence conflicts with persisted expectations | Preserve `details.conflicts` and handle as `ManualReview` or `ConflictSpent`. |

The following constants are also exported, but the current SDK implementation does not guarantee that it consistently produces them as runtime outcomes:

- `WALLET_UNAVAILABLE`
- `ROOT_SIGNATURE_REQUIRED`
- `SIGNER_MISMATCH`
- `DISCLOSURE_UNAVAILABLE`
- `TX_BROADCAST_FAILED`

Do not build catch branches that depend only on these values. Wallet, disclosure, and broadcast paths may fail as a generic `Error`, a provider error, a result object, or a reservation state. If a future release adds a runtime contract for them, update the changelog and this document together.

## Recovery criteria by stage

| Failed stage | Likelihood of reaching the network | Safe next action |
| --- | --- | --- |
| Profile/config validation, `health()`, chain/wallet network mismatch | None | Fix configuration and rerun preflight. |
| Planner returns `canBuildTx: false` or a planner error | None | Resolve balance/note-shape issues from the plan's `status`, `action`, and `facts`, then create a new plan. |
| Payload/config validation fails before the prover call | None | Fix the input, circuit, audit/disclosure, or asset configuration. Release/replan the existing reservation according to the state recorded by the helper. |
| Prover timeout/unavailable/rejected/cancelled | Usually before broadcast, but a proof job or in-process solver may remain | Check the adapter job/checkpoint and current reservation. Do not send the same witness to another endpoint or generate a duplicate proof before reconciliation; retry/replan only afterward. |
| Wallet explicitly rejects signing/submission | None when the explicit provider rejection is known to be before broadcast | Confirm that the SDK helper recorded proof-disposal evidence and `ReplanRequired`. Do not release the note based on a catch alone. |
| RPC broadcast started or its result is ambiguous | Yes | Keep the reservation in `Unknown` and reconcile using the network `txHash`, artifact binding, nullifier, and chain evidence. A Cosmos exact signed `txBytesHash` can link to network identity, but an EVM request-binding hash is not an RPC lookup key. Do not resubmit a new transaction. |
| Tx/receipt explicitly failed | Yes | Confirm both that the input nullifier is unused and that the recorded transaction failed or is absent, then consider `Failed` or `ReplanRequired`. |
| Nullifier confirmed spent | Confirmed | Set the reservation to `ConfirmedSpent`. Determine payment/operation success separately from output evidence. |
| Insufficient or conflicting evidence, or lease/bookkeeping error | Unknown | Isolate as `ManualReview` and inspect operator/chain evidence. |

If a historical Merkle path query returns `ResourceExhausted`, the public non-current rebuild limit has been reached. Do not automatically fail over the same historical request across multiple public providers; replan from the current root or use a trusted local historical-path index. The Clairveil v0.3.1 public limit is 1,024 leaves and two concurrent rebuilds per keeper process; the offline recovery/export limit is 1,048,576 leaves.

## Prover cancellation and retry boundary

`AbortSignal`, an HTTP timeout, or async poll cancellation is **client wait cancellation**. It is not evidence that an in-process solver that already acquired an admission permit was preempted or that its memory was returned. Prover operators must provide hard termination and OOM containment through supervised process isolation.

- `retryable=true`, HTTP 429, timeout, and queue saturation do not grant permission to fail over to another prover endpoint.
- The default policy is one explicitly selected endpoint with automatic failover disabled.
- If a product adapter implements a same-endpoint retry, first check the original payload/checkpoint and whether a duplicate proof job exists. After a general prepare helper has already returned a failure, the reservation may have been released; do not assume that the same reservation is still held.
- Sending the same private witness to an additional endpoint requires explicit user or product-policy approval of the expanded privacy boundary.
- The current general transfer/withdraw prepare helper calls `rollbackPlanReservation(...)` when preparation fails. A valid `Proving` reservation is moved to `Released` through `releaseReservedOrProving(...)`; only an already expired lease makes the best-effort path move to `ManualReview`. This release is not evidence that the solver/job stopped, so products that need async job IDs and checkpoints must track them in a separate operation store.

## Broadcast boundary and `Unknown`

Reservation-aware broadcast helpers record `broadcast_in_flight` and attempt evidence immediately before the external call. They handle the result as follows:

- If a high-level broadcast helper receives a submission identity, set `Submitted`.
- If the transaction may have reached the network but the result is unclear, set `Unknown`.
- If there is an explicit pre-broadcast wallet rejection and proof disposal can be recorded safely, set `ReplanRequired`.
- If the provider response or bookkeeping state cannot be judged safely, set `ManualReview`.

If an error has `reservationReconciliationRequired: true` and `reservationBookkeepingError`, the transaction may have been broadcast or durable state recording may have failed while processing the broadcast result. Preserve the original error and transaction identity, then reconcile immediately.

`signDocHash` supports binding a prepared/signed artifact but cannot create `Submitted` by itself. The current low-level `markSubmitted(...)` does not distinguish transports and accepts either `txHash` or `txBytesHash`, so an EVM canonical request binding can technically create `Submitted`. The high-level EVM send helper records the network `txHash` returned by the wallet/provider. Because an EVM `txBytesHash` is not a receipt lookup key, callers using the low-level manager must not interpret a state name alone as proof of network submission.

## Dual evidence for `Failed` and `ReplanRequired`

Moving from `Submitted` or `Unknown` to `Failed` or `ReplanRequired` requires both conditions:

1. `nullifier_unspent_confirmed`: the input nullifier is confirmed unused.
2. `tx_absent_or_failed_confirmed`: the recorded transaction is confirmed absent or failed.

```js
await reservationManager.transitionBatch(
  reservationIds,
  "Unknown",
  "Failed",
  {
    metadata: {
      nullifier_unspent_confirmed: true,
      tx_absent_or_failed_confirmed: true,
      checked_height: checkedHeight,
      tx_hash_checked: txHash
    }
  }
);
```

Do not skip the nullifier query after checking one failed receipt, or skip the transaction lookup after confirming that the nullifier is unused. If either side is unclear, keep the reservation in `Unknown` or `ManualReview`.

`transitionBatch(...)` is a low-level CAS API for transitions without a dedicated helper. It does not bypass allowed transitions, lease guards, or evidence guards. In normal product code, prefer dedicated helpers such as `markSubmitted`, `markUnknown`, `markReplanRequired`, and `resolveManualReview`.

## `ConfirmedSpent` and operation success

`ConfirmedSpent` means that the input note's nullifier was consumed on chain. Do not report the payment, payroll item, or transfer as successful until all of the following are verified:

- The stored `txHash` or `txBytesHash` and reconciliation evidence contain the same identity. The current generic matcher does not distinguish transports, so an EVM network `txHash`/receipt requirement must be enforced separately by the caller.
- The expected output commitment
- The recipient, amount, denom, or their binding hash
- Disclosure digest and policy evidence
- Every linked reservation in a multi-input operation

When evidence is incomplete, keep the spent input unavailable for reuse and place the operation in `ManualReview`. An explicit mismatch is recorded as `ConflictSpent` and `OPERATION_EVIDENCE_CONFLICT`.

## Resolving manual review

Moving from `ManualReview` to `Released`, `ReplanRequired`, or `Failed` requires operator evidence:

- `operatorId`
- `approvalReference`
- `reason` is recommended for the audit log

The operator must verify the stored payload/proof hash, transaction identity, relay handoff, chain height, nullifier, and output evidence. Do not release a note based only on TTL expiry, local cancellation, or “it has been waiting a long time.”

## Safe logs and user messages

Do not send the following values to logs, analytics, or error-reporting services:

- Privacy root signature and root seed
- Spend/view/disclosure private material
- Note amount, randomness, nullifier, decrypted note, and note plaintext JSON
- Merkle path and prepared payload body
- Prover request/response body, private payload, and proof checkpoint contents
- Disclosure plaintext and the original verification report
- Reservation encryption keys and `indexKey`
- Bearer tokens and raw wallet-provider requests

Operational logs may contain the error code, stage, endpoint origin, non-secret opaque reservation/operation ID, truncated transaction hash, and checked height. Keep the full transaction hash only in an access-controlled operation store needed for transaction lookup and reconciliation; do not place it in ordinary logs, analytics, or crash reports. Do not automatically serialize `error.details`, `cause`, or request bodies; redact from an allowlist.

Show users actionable messages such as “retry available,” “checking the chain,” or “manual review required.” Do not expose internal exception messages or the full provider response.
