# ClairveilJS API Mapping

## Purpose and scope

This document traces how the ClairveilJS APIs called by a browser DApp map to actual **chain REST/RPC**, **prover HTTP contracts**, **Cosmos messages**, and the **EVM privacy precompile**.

It covers high-level flows that communicate with external systems or create transactions, rather than a complete symbol reference for pure crypto, codec, and schema helpers. The package export map's TypeScript declarations are the source of truth for the complete arguments and return types of each method.

- System deployment and trust boundaries: [System architecture](./architecture.md)
- Preventing duplicate note use and recovering after submission: [Note Reservation State Transitions](./reservation-state-machine.md)
- Endpoint and client options: [Deployment and client configuration](./configuration.md)
- Error forms and retry decisions: [Errors and recovery](./errors-and-recovery.md)

## Core v0.6.1 protobuf bindings

The unreleased `clairveiljs/cosmos-v2` entrypoint exports `AuditAuthorizationV2`, `OutputEffectV2`, all seven `Msg*V2` codecs and responses, all six audit query codecs, seven `msg*V2TypeUrl` constants and `createClairveilV2Registry(extraTypes?)`. The root also exports these explicitly suffixed names. Raw generated bindings are available under `clairveiljs/generated/clairveil/privacy/v2/tx` and `/query`, with or without `.js`.

These are wire bindings only: amounts remain strings, protobuf `uint64`/`int64` fields use `bigint`, and byte fields use `Uint8Array`. `createClairveilV2Registry` registers the four asset messages and three administrative messages alongside standard Cosmos messages. It does not register privacy V1 messages. Existing `MsgDeposit` and `createClairveilRegistry` remain V1. The dedicated trusted V2 workflow below composes preparation, audit authorization and proving; importing a codec does not enable those flows or validate a transaction's semantics.

The authoritative generation inputs are the six V1/V2 proto files at Core `v0.6.1`, commit `fad307abddd0daa1c880f2e423668f5c58a0e578`, pinned by `fixtures/clairveil-v0.6.1-proto/manifest.json`. The V1 reserve query includes additive `liability`, `collateralized`, `surplus` and `shortfall` fields. Historical V1 proto bytes moved under `fixtures/clairveil-v0.3.1/proto/`; the original lifecycle fixture source and v0.4.0 deposit prover source remain separate. `supportedClairveilProtoRelease`/`supportedClairveilProtoCommit` describe only this proto source, not runtime protocol support.

`npm run codegen:proto` regenerates TypeScript, JavaScript and declarations. `npm run check:proto-freshness` checks an isolated clean regeneration; `npm run verify:clairveil-source` compares bytes against exact Core commit objects and annotated release tags. `test/cosmos-v2.test.js` compares all populated V2 message shapes and audit responses against 13 independently generated Go vectors, including nested/repeated fields and maximum 64-bit integers. The vectors use synthetic addresses/proofs and do not represent executable transactions.

To reproduce the Go vectors, extract Core `v0.6.1`'s `go.mod`, `go.sum` and `x/privacy/types/v2` into a temporary directory using `git archive v0.6.1 go.mod go.sum x/privacy/types/v2`. From that module directory, run `go run -mod=readonly /absolute/path/to/clairveiljs/tools/generate-v2-proto-vectors.go`. ## Uint128 amount planning (Core v0.6.1)

`clairveiljs/amount` adds `parseAmount128`, `sumAmounts128`, `sumAmountTotals`, `amount128ToJSON` and `amount128FromJSON`, with `maxShieldedAmountV2 = 2^128 - 1`. New amount inputs accept canonical decimal strings or `bigint`, never JavaScript numbers. JSON amount values are quoted decimal strings. `sumAmounts128` checks every input and the sum for one transaction; `sumAmountTotals` handles non-negative arbitrary-precision wallet, payroll and cumulative totals without a uint128 cap. Heights, epochs, account numbers and legacy uint64 wire fields retain their original widths.

`clairveiljs/note128` owns independent `Note128`, `FoundNote128Input` and `NormalizedFoundNote128` types and construction/normalization functions. Only canonical fields are accepted: compact note fields (`am`, `rsx`, etc.) and old cache aliases (`Note`, `NullifierStatus`, `spent`, etc.) are rejected even alongside canonical fields. An explicit 32-byte nullifier is required; missing status stays `unverified`, and `isSpent: true` dominates as `spent`. Heights and sequence normalize to exact uint64 decimal strings, with numerical ordering above the safe-integer limit. Explicit randomness consumes no fresh entropy. These functions validate the field/amount model; full curve, memo and commitment validation belongs to `protocol-v2`. No old note/cache migration is provided.

`clairveiljs/planner-v2` exports `planTransferNotesV2`, `planTransferBatchNotesV2`, `planWithdrawNotesV2`, `selectTransferInputsV2`, `selectBatchTransferInputsV2` and `summarizeSpendableNotesByDenomV2`. It uses the existing bounded selection algorithm with the Core v0.6.1 amount policy: individual notes, requested amounts, selected input sums and payment-plus-change sums must fit uint128. Transfer still needs two inputs (including an explicit zero helper when necessary); batch keeps 1..16 inputs and at most 32 outputs including change. Invalid amounts report `invalid_amount`; a sufficient balance with no valid pair reports `note_preparation_required`. Wallet totals may exceed uint128. Duplicate spendable nullifiers are rejected.

`clairveiljs/reference-payroll-v2` exports `normalizePayrollInputV2` and `planOneProofPayrollV2`. The planner splits a payroll exceeding uint128 into separate bounded operations using distinct current notes, preserves owner/reservation/output-capacity boundaries, and reports unbounded `total_payroll_amount` and `total_spendable_amount`. It does not spend hypothetical future change. Each plan/operation carries `amount_model: "uint128"`, operation IDs have a `:uint128` suffix, and no circuit identity is asserted. V1 preparation rejects these plans even for small amounts. These are amount plans, not proof-ready transactions; a `canBuildTx` flag in the note planner means amount/input eligibility only.

The dedicated V2 entrypoints implemented in 01–04 (`amount`, `note128`, `planner-v2`, `reference-payroll-v2`, `protocol-v2`, `audit-config-v2`, `cosmos-v2`) have no runtime or declaration dependency on V1 execution modules. Pure planning/DTOs, hash domains and validation primitives are shared; payroll execution and audit querying are separated. Import V2 payroll from its dedicated entrypoint or root/core; its forwarding exports through old `reference-payroll` are removed. Unreleased V1 input/cache compatibility is not part of V2. Explicit V2 workflow/scan/proving/transaction entrypoints are implemented below; the broad root retains V1 compatibility APIs. Core's current `v1` hash domains and configuration protobuf namespace remain protocol constants.

Core `v0.6.1@fad307abddd0daa1c880f2e423668f5c58a0e578` owns the amount rules (`x/privacy/amount/amount.go`, `x/privacy/types/amount.go`, `x/privacy/client/sdk/transfer/transfer.go` and `x/privacy/client/sdk/payroll/batch_plan.go`). `test/amount-planner-v2.test.js` checks zero, 2^64, uint128 max, malformed/numeric JSON, overflow, exact change, bounded selection, wallet totals and payroll splitting. The 18 parse and six addition reference cases in `fixtures/clairveil-v0.6.1-amount/vectors.json` were generated with Core Go, including its quoted JSON representation; source verification checks the source file hash against the pinned commit. Reproduce by extracting `go.mod`, `go.sum` and `x/privacy/amount` from that tag into a temporary directory and running `go run -mod=readonly /absolute/path/to/clairveiljs/tools/generate-amount-vectors.go` there. Stdout must match the fixture bytes.

## Fixed-v2 codec (Core v0.6.1)

`clairveiljs/protocol-v2` (also exported by root/core) implements `privacy-fixed-v2`, binary version 2. Note and disclosure amounts occupy 16 bytes in big-endian order. The SHA-256-derived 16-byte tags use `clairveil.note-plaintext.v2`, `clairveil.disclosure-plaintext.v2` and `clairveil.encrypted-envelope.v2`. Core retains Go names such as `Note` and `MarshalNotePlaintextV1`; the explicit JS V2 names select the new wire bytes. Note commitment/nullifier, asset and view-tag hash domains retain their existing Core identities.

| Payload | Exact bytes |
| --- | ---: |
| Note plaintext / disclosure plaintext | 358 / 400 |
| Deposit note envelope / transfer note envelope | 406 / 438 |
| User / audit / self-view disclosure envelope | 480 |

`validateNoteV2`, `marshalNotePlaintextV2`, `unmarshalNotePlaintextV2`, `computeNoteCommitmentV2` and `computeNoteNullifierV2` validate uint128 amounts, canonical BN254 fields, non-identity prime-subgroup keys and a UTF-8 memo of at most 128 bytes. `validateDisclosurePlaintextV2`, `marshalDisclosurePlaintextV2` and `unmarshalDisclosurePlaintextV2` enforce user policies 1..7, matching bitmaps and zero sentinels for hidden fields, or the full-disclosure marker. Decoders reject wrong lengths, domains, versions, reserved bits, noncanonical fields and legacy payloads. `decodeEncryptedEnvelopeV2` returns detached ciphertext bytes; `unwrapEncryptedEnvelopeV2` additionally requires the expected kind.

`encryptDepositNoteV2`/`decryptDepositNoteV2` require a 32-byte RootSeed and use the Core AES-GCM seed-key format. `encryptNoteForTransferV2`/`decryptTransferNoteV2` and `encryptDisclosureV2`/`decryptDisclosureV2` use the existing Edwards ECIES/AES-GCM primitives. Transfer encryption checks that the supplied commitment matches the note. Optional transfer-decryption binding requires the commitment, output index and 2-byte view tag together and verifies both the tag and recovered note commitment. Disclosure encryption/decryption checks the expected user/full plane. Private scalars must be nonzero and strictly below the subgroup order; entropy failures propagate without fallback.

`computeDisclosureDigestV2(payload, scheme)` and `verifyDisclosureDigestV2(payload, expectedDigest, scheme)` require an explicit `"transfer"` or `"batch"` scheme because the circuits use different field orders and domains. Digest verification rejects a mismatch against a canonical nonzero 32-byte expected digest. Raw decoding/decryption alone does not verify an external digest or chain metadata. These are fixed-wire/cryptographic compatibility helpers, not scan admission, audit-field authorization, transaction preparation or a claim of native constant-time execution. Existing V1 entrypoints keep their original wire behavior.

`test/protocol-v2.test.js` compares four note boundary cases, all seven user policies and full disclosure against independent Core Go output. It checks exact plaintext, commitment/nullifier, both disclosure digest schemes, deposit/transfer/disclosure ciphertext and view-tag bytes, with rejection tests for malformed inputs and V1/V2 cross-use. Keys, seeds and deterministic entropy in `fixtures/clairveil-v0.6.1-fixed/vectors.json` are public synthetic test data. Production functions always use the runtime CSPRNG; no deterministic test hook is exported.

To regenerate, extract Core `v0.6.1@fad307abddd0daa1c880f2e423668f5c58a0e578` with `git archive v0.6.1 go.mod go.sum types internal/strictjson x/privacy/amount x/privacy/types x/privacy/crypto` into a temporary directory. Run `go run -mod=readonly /absolute/path/to/clairveiljs/tools/generate-fixed-v2-vectors.go` there on a platform supported by Core's native secret profile. Stdout must exactly match the fixture. The release source test checks all 12 recorded source hashes against that commit. Go's fixed-v2 functions generate the reference bytes and decrypt their generated ciphertext; the JS test also reproduces those exact encrypted bytes.

## V2 audit configuration and key snapshots

`clairveiljs/audit-config-v2` (also root/core) provides `queryActiveAuditSnapshotV2`, `computeAuditNetworkDigestV2`, `parseAuditKeyRecordV2`, `validateAuditCircuitIdentityV2`, `validateAuditArtifactManifestV2` and `assertAuditSnapshotCurrentV2`. `ClairveilJS.queryActiveAuditSnapshotV2(options)` uses the configured chain ID and one REST endpoint throughout the query. Its required local inputs are a complete deployment-owned circuit identity, exact artifact manifest bytes and an independently pinned SHA-256 digest. Optional `expectedNetworkNonce` and `expectedInitialHeight` pins detect an unexpected genesis namespace; the caller still owns authenticated chain provenance.

The preflight queries `/clairveil/privacy/v2/audit/configuration`, then `/clairveil/privacy/v2/audit/key_schedule` and `/clairveil/privacy/v2/audit/keys/{epoch}`, sending `x-cosmos-block-height` from the configuration to both later requests. All three response heights must match. Halt, missing/zero epoch, malformed pending schedule, pruned or ignored height, conflicting aliases, circuit/VK/schema mismatch, wrong local artifact digest and invalid key records reject the promise before a preparation snapshot is returned. No latest-height, V1 or alternate-endpoint fallback occurs. Custom providers implement `configuration({})`, `keySchedule({height})` and `key({epoch,height})`; they must honor the supplied height. REST responses use canonical base64 and decimal strings; generated responses may use bytes and bigint. `halted` must be explicitly boolean; integers cannot use JS numbers.

The exact 261-byte Core key record uses suite 2 and Point64 (big-endian x||y), distinct from the legacy compressed key. Parsing checks metadata, initial/rotated epoch rules, canonical coordinates, nonidentity and prime-subgroup membership, the deterministic KeyID and the Schnorr PoP bound to network, epoch and activation height. The network digest binds chain ID, 32-byte genesis nonce and the audit circuit set. All snapshot integers are decimal strings, including full uint64 epochs and int64 block heights; byte identities are lowercase hex. The returned snapshot and its nested objects are immutable and carry no private material.

Manifest checking validates the four ordered audit circuits and 12 R1CS/PK/VK descriptors against Core's schemas and the deployment pin, then hashes the exact local bytes as Core's CLI does. It reports the development marker but does not load artifact files, verify a proof or qualify setup trust. Independently authenticated chain views and trusted local artifacts remain the host's responsibility. A matching RPC response alone is not consensus authentication.

Before proving or broadcasting, re-query and call `assertAuditSnapshotCurrentV2(previous, current)`. Newer heights with the same network/epoch/key/artifact namespace are allowed; rollback, namespace changes and copied/deserialized snapshots are rejected. This comparison does not itself fetch current state. The API is a V2 preparation preflight; the existing V1 wallet/prover/submission paths are unchanged, and full proof-witness construction and V2 transaction submission remain later scope; proving and local verification are described below. Audit authorization construction is described below.

`fixtures/clairveil-v0.6.1-audit/vectors.json` contains public synthetic Core Go vectors for four records (initial, rotated, above-safe-integer and maximum uint64 epochs), 11 invalid records, network digest, protobuf identity and manifest bytes. Reproduce by extracting `git archive v0.6.1 go.mod go.sum types internal x/privacy` into a temporary directory and running `go run -mod=readonly /absolute/path/to/clairveiljs/tools/generate-audit-v2-vectors.go` there on a supported Core native profile. Stdout must match exactly. Release tests compare all ten source hashes with `fad307abddd0daa1c880f2e423668f5c58a0e578`; focused tests also exercise same-height REST headers, halt, malformed inputs, rotation and artifact changes.

## V2 audit authorization and public binding

`clairveiljs/audit-authorization-v2` is a wallet-local construction layer for deposit (1), withdraw (2), transfer2x2 (3) and batch16x32 (4). `createAuditOutputEffectV2(kind, index, effect)` copies fixed-v2 recovery/disclosure bytes into the generated `OutputEffect` shape and checks policy, position, exact framing, canonical fields/points and public disclosure metadata/digest. Use `protocol-v2` to produce the underlying encrypted note/disclosure bytes. Deposit and 2x2 change output disclosure fields must be omitted. `encodeAuditAuxV2` checks output counts, order and duplicate commitments and uses the exact Core Aux framing.

`buildAuditPublicInputsV2({kind, snapshot, message})` returns PI21 from proofless generated V2 message fields, or PI23 when `message.audit` is present. It binds the authenticated snapshot namespace, expiry, root, nullifiers, ordered effects, disclosure vector roots and transparent amount/asset/address. Cosmos addresses use the current `clair` prefix; deposit permits zero, withdrawal must be positive, and public coin amounts fit uint128. `parseAuditEnvelopeV2` strictly checks suite/version, reserved bytes, counts, size, canonical fields and subgroup points. Public Poseidon2 cipher roots, context hashes and owner intents match Core. `verifyAuditMessageBindingV2` rebuilds PI23; it does **not** verify a proof or authenticate/decrypt ciphertext. Nondeposit creator is not part of Core PI23; the prepared object separately requires the original creator.

`prepareAuditAuthorizationV2` takes proofless `message`, a branded `snapshot`, private `plaintext` BE32 fields, a trusted local `backend`, and mandatory `getCurrentSnapshot`. The plaintext has exactly 6/2/13/177 fields in Core order: deposit `[asset, amount, spendX, spendY, viewX, viewY]`; withdrawal `[asset, inputCommitment]`; transfer/batch `[asset, inputCommitments..., output(amount, spendX, spendY, viewX, viewY)...]`. Batch uses 16 input and 32 output slots with zero padding. Canonical field/count checks are performed here; note ownership, amount conservation, paths and correspondence between these private fields and the full witness belong to the subsequent circuit/proving step. Callers must not treat this object as a proved transaction.

The backend independently samples fresh encryption randomness and nonce using Core's supported native secret profile. Preparation rechecks snapshot and expiry both before and after encryption. `messageData()`, `publicInputs()` and `ownerIntent()` return detached public copies. Private randomness is available only through explicit `exportEncryptionWitness()`; the trusted prover coordinator must clear that copy. `assertCurrent()` re-queries and clears the preparation on failure; expiry/abort on use and `clear()` also invalidate it. JSON serialization is disabled and inspection is redacted. Clear is best effort: JavaScript/Go garbage collectors can retain copies. Never send plaintext, randomness or this object across the DApp provider boundary or persist it as JSON.

`clairveiljs/audit-native-node` is Node-only. Build an explicit local binary with `node tools/build-audit-native.js /path/to/clairveil /path/to/output/encrypt`, then call `createAuditNativeBackendV2({executablePath, sha256})` using a trusted build's independently pinned SHA256. The build extracts exactly Core commit `fad307abddd0daa1c880f2e423668f5c58a0e578`, requires all four native known-answer tests, and writes nonsecret build provenance next to the binary. The adapter executes a private copy of the verified bytes, uses bounded binary stdin/stdout without secret arguments/logs/files, enforces timeout/cancellation and removes the temporary executable. No HTTP, JS/WASM secret-crypto or unsupported-profile fallback exists. Browser public APIs can be bundled; an actual extension-to-native-host transport is separate host work and is not installed here.

`npm run verify:audit-native -- /path/to/clairveil` builds and runs native integration tests (requires a supported Core Go/native toolchain). The ordinary unit suite does not require a native executable; its native integration case is explicitly skipped unless the binary/hash environment pins are provided. `test/audit-authorization-v2.test.js` checks ten independent synthetic Go cases, all three disclosure modes, zero/max uint128, max batch, malformed frames, mutations, rotation, expiry and secret lifetime. Regenerate the fixture in an extracted Core module with `go run -mod=readonly /path/to/clairveiljs/tools/generate-audit-authorization-v2-vectors.go /path/to/clairveiljs/fixtures/clairveil-v0.6.1-audit/vectors.json`. The fixture and bridge contain no user material. The trusted V2 workflow below supplies full note-to-witness construction; ordinary chain signing/submission remain host-owned. The proving coordinator and local verification are described below.

## V2 proving and local verification

`clairveiljs/audit-prover-v2` exports `createAuditProverV2({baseUrl, verifier, fetch?, timeoutMs?, bearerToken?})`. The explicitly selected prover receives the complete private witness; use a locally or independently controlled prover. Only HTTPS origins or HTTP loopback origins are accepted. The client sends one `POST /v2/prover/audit-field`, with the current Core envelope literal `version: "v1"`, exact circuit/set/artifact identity, PI23 and witness as canonical base64. This envelope literal is current V2 protocol, not a legacy fallback. Redirects, retries, endpoint discovery, ambient cookies and V1 calls are disabled.

`await prover.prove({prepared, witness, signal?})` consumes a genuine object from `prepareAuditAuthorizationV2`. The witness must be complete gnark BN254 binary encoding: three big-endian uint32 counts (public=23, secret>0, total=public+secret), followed by canonical BE32 fields in public-then-secret order. Maximum witness size is 4 MiB; all 23 public fields must exactly match the prepared PI23 and trailing bytes are rejected. This accepts a full witness built by the trusted wallet/Core builder; it does not construct note secrets, Merkle paths or owner signatures. The input byte array is copied and cleared before any await. The preparation is synchronously claimed for one attempt and cleared on success, failure, timeout or cancellation. Concurrent/repeated attempts cannot reuse it. Callers own any other private copies, which must also be cleared.

The default 120-second deadline (configurable 1..3,600,000 ms) covers snapshot refresh, HTTP headers/body and local verification. Snapshot/expiry checks run before export, after the response and after verification, with a synchronous abort/preparation fence before dispatch and return. Responses are streamed under a 16 KiB limit and parsed with duplicate-key, unknown-field, UTF-8, canonical-base64 and exact ordered PI23 checks. Canonical 164-byte proof framing alone is insufficient: a mandatory trusted `AuditProofVerifierV2` must complete the local curve/pairing check and return literal `true`. The coordinator then returns detached generated V2 message fields including proof. It never signs or submits. `AuditProverErrorV2.code` identifies request/snapshot/transport/response/verification/aborted/timeout failures; remote bodies, bearer tokens, private abort reasons and verifier diagnostics are not included.

The Node-only `clairveiljs/audit-verifier-node` provides `createAuditNativeVerifierV2({executablePath, sha256, artifactDirectory, expectedArtifactHash, expectedCircuitIdentity, timeoutMs?, executionMode?})`. Build its binary with `node tools/build-audit-native.js /path/to/clairveil /path/to/verify verify`. Independently pin the trusted executable SHA256, exact manifest SHA256 and complete circuit identity. Construction validates the manifest and all four VK hashes; each check uses immutable copied bytes and the exact selected circuit. It loads no PK/R1CS, invokes no downloader and reads no artifact environment overrides. The Core registry decodes/re-encodes canonical VK/proof bytes and performs BN254 Groth16 verification with PI23. Core v0.6.1 permits this audit bundle only with its explicit development marker; these APIs do not qualify a setup for production.

`npm run verify:audit-prover -- /path/to/clairveil` extracts the pinned Core commit, generates temporary single-party development artifacts for all four **actual Core circuits**, proves and verifies each, and tests all 23 PI mutations plus circuit/key/artifact/proof rejection. It also runs JavaScript authorization → the actual Core loopback HTTP prover → the pinned local verifier → generated V2 deposit encoding with a uint128 amount above uint64. Native timeout, cancellation and output bounds are checked. The command fails on missing/skipped required cases and removes its temporary setup; optional second argument is an exact-source/hash-checked development fixture cache. The ordinary unit suite explicitly skips the three native integration cases when their fixture/binary pins are absent. The test server uses synthetic data and is never installed as a product service.

Browser-safe transport and declarations bundle independently of V1 execution and Node-only binaries. A browser host must supply a qualified local verifier bridge; this change installs no extension native-host transport. Never put the preparation, plaintext or full witness on the DApp provider boundary or persist/log them. JavaScript strings, caller copies and garbage collectors prevent guaranteed secret erasure. The host owns native installation, origin admission and ordinary-wallet UI/submission integration; this SDK does not install an extension or a native host.

`preparation-v2` builds fixed-v2 deposit material and validates selected uint128 spend inputs, including owner, asset, nullifier, aggregate amount and exact-match withdrawal. `prepareAuditWitnessV2` in `audit-witness-v2` then checkpoints approved intent/reservations, refreshes the snapshot, invokes a trusted native backend, and binds its complete deposit/withdraw/transfer witness to the approved inputs and audit message. `audit-witness-node` executes hash-pinned bytes of `tools/audit-witness-bridge.go` built inside pinned Core. Core owns output recovery, disclosure, final owner signing and witness construction. A fresh snapshot pins the host account prefix (`clair` by default, explicitly `maroo` for Maroo). No old codec or legacy event fallback is allowed.

Both `createAuditWitnessNativeBackendV2` and `createAuditNativeVerifierV2` accept `executionMode: "staged" | "installed"`, defaulting to staged immutable copies. Installed mode is for an operator-provisioned native host: it requires an absolute, nonsymlink executable path, trusted current-user/root ownership, non-group/world-writable file and parent directories, a regular executable file and the exact pinned SHA-256 before execution. File reads are bounded and use `O_NOFOLLOW`. It executes the installed binary directly without creating a new executable under the browser process. It does not disable OS security controls or defend against compromise of the same OS owner/administrator. The native helper is inside trusted custody and may receive selected notes and a derived spend scalar, but never RootSeed; the separately approved prover receives only the reviewed witness. `test/native-installed.test.js` checks pins, mutation, symlink and unsafe-permission rejection.

`transactions-v2` builds the three explicit Cosmos V2 messages/sign documents and EVM transactions from locally verified public proof fields. The DApp's artifact verifier selects `protocol: "audit-field-v2"` explicitly and binds the exact approved actor, effect, amount and transport envelope; omitted protocol retains `note-v1`. Public wire/ABI modules are isolated from private preparation, codec cryptography and witness modules. Public structural checks do not replace the trusted host's complete cryptographic validation.

The public wallet API schema permits canonical uint128 individual/operation/disclosure amounts, with digest `33be71b39bfe6a974a8ce1154e5fcf28b25a898deb72eb26a10214587d65313b`. Heights, epochs, expiry and revisions retain uint64. Legacy execution profiles still impose their uint64 amount limit. Hosts advertise only supported methods; V2 transaction audit data does not imply optional page disclosure-query support.

`evm-v2` encodes the three direct Maroo requests from `IPrivacy.json` at `823f6752e89a8d7157bd90973e7b1f9093e0ec10` (Core v0.6.1). Independent go-ethereum vectors cover the ABI; encoding alone does not validate the proof, chain actor, contract or exact payable deposit value. `reserve-v2` follows Core's liability/collateralization arithmetic, accepting surplus and reporting shortfall separately. `scan-v2` validates audit identity and fixed-v2 output framing with the shared pagination engine; `note-store-v2` is a private storage representation that must be encrypted by the host. A failed or missing nullifier refresh never preserves cached spendability. V2 continuation/cache identities reject older data and require a rescan without discarding known pending reservations.

## Trusted V2 workflow and disclosure

`clairveiljs/wallet-kernel-v2` exposes `prepareAuditTransactionV2`. It requires the explicit V2 witness input, native backend, `assertAuthority`, durable `checkpoint`, same-deployment `getCurrentSnapshot`, and prover options including a mandatory local verifier. It copies the RootSeed, checks authority before and after asynchronous boundaries, commits approval/reservations before native owner signing, consumes the complete witness through the V2 prover, verifies the proof locally and rechecks the snapshot before returning `{kind, message, snapshot}`. Owned seed/request/witness buffers are cleared on success and failure; the caller owns its original seed and private inputs. No ordinary-wallet signing, automatic resubmission or reservation release occurs. Use `transactions-v2` after a final host/account/fee preflight. The page example `examples/custody-v2-flow.js` imports only public DApp code; it never derives or receives privacy material.

`clairveiljs/disclosure-v2` exposes `decodeUserDisclosureFromScanOutputV2` and `decodeSelfViewDisclosureFromScanOutputV2`. Only integrity-checked outputs from `scan-v2` are accepted. Direct transfer output 0, plane/policy, tx hash, commitment, fixed-v2 plaintext, authenticated decryption, transfer digest and optional asset-denom binding must match. Public and recipient-encrypted user disclosure plus self-view support uint128. The trusted result contains full decoder metadata; a custody host must project its approved field allowlist before page delivery. This does not decode the separate mandatory auditor field and does not enable batch or raw event fallback.

`verify:release:integration` now requires `verify:release:audit`. Supply `CLAIRVEIL_SOURCE_DIR` and `CLAIRVEIL_AUDIT_ARTIFACT_CACHE`, or pass the two paths to the standalone gate. The cache must match exact Core archive/generator bytes and all four circuit file hashes. Both historical raw-generator and normalized-generator provenance are accepted only when their declared hashes match; no provenance is rewritten. Native verification and the six full preparation/proof/encoding cases cannot skip. This is a development cryptography gate; the consuming host still needs actual ordinary-wallet/chain qualification.

## Trusted RootSeed identity (CC-002)

The unreleased `clairveiljs/wallet-kernel` entrypoint starts the CC-002 extraction with `createPrivacyIdentity({ rootSeed, shieldedPrefix? })`. It accepts a 32-byte `Uint8Array` already held by the trusted wallet runtime and copies it before deriving spend, view and disclosure keys with the existing protocol algorithms. Custody generates and backs up fresh entropy; this constructor does not generate a seed, request a root signature or contact an ordinary wallet. Other input fields, including legacy signature material and chain actors, are rejected.

The returned `WalletPrivacyIdentity` contains the copied RootSeed and private key pairs and stays inside the trusted runtime. Its frozen `publicIdentity` projection contains only `shieldedAddress`, `spendPubKeyHex`, `viewPubKeyHex` and `disclosurePubKeyHex`. This projection is an internal SDK type, not a custody RPC account DTO or a permission to disclose it. Custody still owns grants, public DTO projection, vault persistence and secret lifetime; JavaScript does not guarantee erasure of all key copies.

Ordinary account/network selection is maintained separately and is not constructor input. Reusing the same RootSeed preserves the privacy keys; `shieldedPrefix` changes address encoding only. The new entrypoint does not wrap or inherit the legacy `PrivacyMaterial` object, and does not add address/signature placeholders to satisfy existing transaction builders. Ordinary chain adapters are separated below; private workflows now accept these two independent inputs as described below. Existing legacy entrypoints and their exact derivation vectors remain unchanged; the new surface is not reexported through the broad root or DApp entrypoints.

`test/wallet-kernel.test.js` directly loads the pinned sender/recipient Go vectors without a skip path. It checks exact scalar/public-key/address correspondence, independent synthetic seed construction, copied input ownership, public projection and rejected legacy/invalid input. The test also runs under `test:conformance:required`; TypeScript checks cover the new package export and rejected secret/actor fields.

## Ordinary chain wallets (CC-002)

The unreleased `clairveiljs/chain-wallet` entrypoint exports `createKeplrChainWalletAdapter`, `createOfflineSignerChainWalletAdapter` and `createEip1193ChainWalletAdapter`. These are ordinary wallet primitives, separate from the legacy root-signing adapters. They import no wallet kernel, private workflow or prover module, expose no privacy-root or typed-data signing method, and are not reexported from the broad root or DApp entrypoints. Existing legacy adapters and vectors remain unchanged.

All constructors require an explicit `chainId` and perform no wallet calls. `connect()` explicitly enables Keplr or requests EIP-1193 accounts; the offline signer only reads its accounts. `getActor()` reads already available accounts without requesting access. Cosmos returns `{ namespace: "cosmos", chainId, address, pubKeyHex }`; EVM returns `{ namespace: "eip155", chainId, address }`. These frozen public snapshots are local SDK types, not custody RPC DTOs, CAIP-normalized account IDs, grants or authenticated privacy-account links. Cosmos uses a native chain ID, an optional pinned address and a Bech32 prefix (default `clair`) with a 20-byte address. EVM requires canonical hexadecimal chain IDs, normalizes addresses to lowercase and optionally pins an account.

`signDirect(signDoc, actor, { signal }?)` and `sendTransaction(transaction, actor, { signal }?)` require a separately captured actor. Before awaiting account discovery they copy the actor and project the input onto public fields; immediately before dispatch they compare the current account/network (and Cosmos public key) to that actor. EVM also reads the network before and after account discovery. The optional `AbortSignal` is captured before any await and checked again after the final account lookup, immediately before calling the wallet without another await. Custody submission always supplies this signal and aborts it synchronously on provider invalidation. Custom adapters and wrappers must preserve and honor it at that same dispatch boundary. A detected mismatch or aborted signal fails before signing or sending; it does not undo a wallet call that already started. Each invocation dispatches at most once and never falls back to a root signature, another wallet or another network.

Cosmos copies `bodyBytes` and `authInfoBytes`, requires the configured chain ID and a uint64 `bigint` account number, and omits extra fields. Keplr receives a real unsigned `Long` from pinned `long` 5.3.2, plus `preferNoSetFee` and `preferNoSetMemo`; the caller document and offline-signer `bigint` contract stay unchanged. The provider input declaration uses `KeplrSignDoc`, and `test/types.ts` compiles against the actual pinned `@keplr-wallet/types` 0.13.41 interface (with `@types/long` 4.0.2 for its Long 4 dependency), not a self-declared mock. These type packages and Keplr's Starknet peer are development-only dependencies. The returned direct-sign response remains wallet-supplied: callers must verify its signed bytes, public key, signature and intended effect before broadcast. This adapter does not broadcast or claim wallet responses are verified.

Keplr's protobufjs `Long` response is normalized from its two 32-bit words to an exact uint64 `bigint`, including values above `2^63` returned with `unsigned:false`; no floating-point conversion or wallet-supplied coercion is used. This preserves the signed protobuf value and does not bypass the submission coordinator's exact document/signature checks. SDK Bech32 decoders pass explicit finite limits (90 for ordinary addresses, 200 for shielded addresses), avoiding the incompatible `Infinity` default in CosmJS encoding with newer `@scure/base` consumer resolutions. The local custody integration harness exposed both issues using actual Keplr signing and a freshly installed packed SDK.

EVM requires `to`, binds `from` and `chainId` to the actor, and accepts only `data`, `value`, `gas`, `gasPrice`, `maxFeePerGas`, `maxPriorityFeePerGas` and `nonce` in addition to those fields. Data must be hexadecimal bytes and numeric fields canonical hexadecimal quantities. Extra metadata is omitted. Contract creation, access lists and typed-data signing are outside this initial surface. `eth_sendTransaction` must return a 32-byte transaction hash; a rejection or malformed reply after dispatch never causes automatic replay. Callers must retain an unresolved submission until reconciliation establishes its outcome.

These provider reads cannot atomically freeze the external wallet while its UI is open. Custody's grant/epoch checks, `beginSubmission` journal, signed-artifact validation and finality/effect reconciliation remain required at the workflow layer and are not implemented by this primitive. Neither these adapters nor the RootSeed constructor make the existing DApp client custody-ready.

`test/chain-wallet.test.js` uses synthetic providers to check stale accounts/keys/networks, input mutation while discovery awaits, explicit connection, public field projection, failure without replay and independent identity retention. Its source import-graph check permits only the local chain-wallet modules, `@cosmjs/encoding` and `long`; an actual browser bundle must also be audited when dependencies change. The tests run under required conformance, and TypeScript checks reject missing/wrong actors, private fields and legacy root-signing calls. Real-wallet and chain/prover qualification remain separate gates.

## Custody SDK surfaces (CC-002)

`clairveiljs/wallet-api` owns the single editable draft in `src/wallet-api/schema/`. `npm run generate:wallet-api` generates DTO types, registry and Ajv 8.17.1 Draft 2020-12 standalone validators; `npm run check:wallet-api` rejects stale output. All 15 methods have closed DTOs. Generated types describe shapes; runtime validation also enforces conditional constraints. Strict JSON parsing rejects duplicate keys, malformed UTF-8/Unicode, accessors, prototypes and byte/depth/list-limit violations. Results are copied/frozen and correlated to method/IDs, the reviewed digest and requested balance assets. `node tools/sync-wallet-api-mirror.js --check|--write CUSTODY_REPOSITORY` checks or updates four generated custody mirrors; edit only the SDK source.

`createWalletKernel({ identity, client, evmClient?, evmChainId?, checkpoint, assertAuthority, reservationManager? })` is trusted-runtime-only. It offers `scan`, `proveDeposit`, `prepareDeposit`, `prepareTransfer`, `prepareWithdraw`, public identity projection and disposal. Transactions require a separate `actor` and `operationId`; scan ownership follows the privacy identity. Existing private client methods accept `privacyIdentity`/`chainActor` separately from legacy `material`/`wallet`. Note, intent signing, audit/self-view, Merkle, nullifier, planner, proof and reservation algorithms are reused. EVM's numeric wallet chain ID is pinned separately from the protocol chain string. Own deposits and native transfers/withdrawals reuse existing Cosmos/EVM builders; third-party deposits, relaying and batch are absent from this facade.

The host supplies authoritative profile/time, encrypted storage and live permission/epoch checks. `checkpoint` must atomically persist the exact operation/export barrier and reservations before resolving. The kernel awaits it and rechecks authority before invoking the explicitly selected prover; checkpoint failure prevents export. After the final asynchronous authority helper returns, deposit/transfer/withdraw each check disposal synchronously with prover invocation, so disposal in an intervening microtask blocks export. The same synchronous fence applies to the final return of scan, deposit proof and all three preparation results; disposal between the final authority helper and return rejects the completed result. `proveDeposit` declares the actual `DepositMaterial` and string/byte proof union accepted by `prepareDeposit`; non-string EVM `proofHex` responses are rejected. Scan declares `privacyAccount` as `PublicPrivacyIdentity`. Strict TypeScript regression coverage connects proof to deposit preparation and reads the scanned public identity without casts. The host must dispose the kernel on runtime authority loss; the asynchronous hook alone is not an atomic revocation subscription. Existing reservation rollback quarantines failures after proving starts. These hooks are integration obligations, not an implemented vault/journal. Kernel results contain private notes/witnesses and must never cross public DTOs. Disposal blocks new work and clears owned byte arrays, without promising erasure of every JavaScript secret copy.

`clairveiljs/custody-provider` exports `createCustodyProvider` and `createDirectBridgeTransport`. Transport and invalidation subscription are explicit. The exchange host authenticates origin/document or topic; the adapter does not implement extension authentication, grants or a WalletConnect responder. Construction performs no I/O. Discovery must match the pinned schema before other methods. Pending requests, timeout and polling are bounded; invalidation discards capability/revision state and late replies; disposal is permanent. Errors use only fixed schema fields. After successful discovery, a listed method absent from capabilities returns `4102 UNSUPPORTED_CAPABILITY`; missing discovery or an invalidated attachment remains `4103 UNAUTHORIZED`, and an unknown method remains `-32601`. After bounded JSON capture, unsupported string `protocolVersion`/`schemaRevision` values return `4101 UNSUPPORTED_VERSION` before exact-params or discovery admission; missing/non-string version fields remain `-32602`. Discovery does not accept a schemaRevision field. Both direct transport and provider use this shared check without invoking getters. Capabilities are compared as bounded JSON values: object key order, including nested objects, does not invalidate the attachment; changed values or array contents/order still do. Equivalent discovery replies preserve polling and revision guards. The nested operation in `cancelOperation` is correlated with the requested operation ID and participates in the same monotonic revision tracking as direct operation results. A stale cancel result or a delayed poll older than an accepted cancel result is rejected with a sanitized internal error; the public nested response shape is unchanged.

`clairveiljs/dapp` exports `createClairveilDappClient({ custodyProvider })` with 15 logical methods and no `.cosmos`, private callback or automatic legacy fallback. Adding `chainWallet` and explicit `validateArtifact` enables `submit`; Cosmos also requires `broadcastCosmos`. `createArtifactVerifier` pins chain/asset/profile digest and EVM contract/protocol chain, decodes allowlisted protobuf/ABI and checks public effects. Cosmos self-merge/final-transfer messages must match the public summary expiry, just as EVM transfers do; missing or different expiry stops submission before begin, signing or broadcast. The approved digest binds all bytes, actor and fees; private intent and fresh chain-state checks remain in custody. A digest supplied by an untrusted page is not approval.

`submit` preserves the caller's begin idempotency key and derives each report key with SHA-256 over the domain `clairveil-custody/submission-report/v1`, begin key, operation ID, attempt ID, outcome and optional normalized hash. Exact report intent reproduces its key; submitted and unknown reports never share the begin key or one another's key. Derivation adds an asynchronous boundary, so attachment authority is rechecked immediately before reporting. A lost report response never permits another wallet invocation.

Submission consumes each permitted begin response once per provider attachment before a wallet call, shares in-flight/attempt guards across clients and rejects stale revisions/epochs/accounts. Cosmos verifies exact signed document, key and secp256k1 signature before one broadcast; EVM requires the explicit EIP-1559 artifact. Cosmos preserves an independent approved document and byte arrays for verification, so even a custom adapter that mutates its input cannot redefine the approved bytes. Uncertain/rejected responses are reported unknown, with no dispatch retry. Memory guards complement the host's durable `beginSubmission` journal and cannot replace it after process loss. `clairveiljs/legacy-browser` explicitly aliases the previous secret-bearing browser client; old `browser-dapp` remains legacy and is never chosen automatically.

The provider keeps admission, capability/revision state and request cleanup in `custody-provider/provider.js`; `direct-bridge.js` only frames and correlates JSON-RPC. `chain-wallet/cosmos-signing.js` owns public sign-document copying and the two Keplr conversion directions. Both ordinary adapters use `dispatchToActor` in `chain-wallet/actor.js` so the final actor/abort checks and actual wallet call share one synchronous continuation; the submission coordinator reuses the same actor comparison. Submission tests share client/profile and synthetic-signature fixtures while keeping each failure injection and assertion explicit. The public entrypoint still exports the same two constructors. Submission stages explicitly separate artifact validation, begin, synchronous attempt consumption, dispatch and reporting. Each submission subscribes to attachment invalidation, passes an abort signal into the chain adapter and removes the subscription on every completion path. Kernel helpers separate actor capture, execution building and checkpoint payload construction. `activeResult` centralizes the final result check and return without adding an async boundary; final prover checks stay synchronous with invocation. EVM proof normalization uses explicit hex and string/byte branches. Workflow declarations retain exactly the same tokens with readable field layout; kernel tests share construction, EVM context, canonical deposit replies and microtask scheduling while retaining explicit failure assertions. Regression cases exercise reserved control slots, timeout cleanup, transport envelope mutation, repeated attempt IDs across clients, attachment loss at every account/network lookup inside the real SDK adapters, attachment loss after Cosmos signing, subscription cleanup and disposal during a checkpoint. The optional dispatch signal and Keplr input declaration refine the SDK adapter contract; wire schemas, protocol algorithms and trust boundaries are unchanged.

New wallet-api/provider/submission/kernel-workflow/public-boundary tests run in default and required conformance suites. Synthetic Cosmos/EVM deposit, transfer and withdraw preparation uses existing private algorithms with mocked chain reads and framed proof replies. Checkpoint loss, actor/epoch changes, signature/calldata mutation and public import graphs are covered. Actual proving, live wallet/chain settlement, encrypted-host fault injection and WalletConnect qualification remain separate. Browser bundle/CSP and immutable package measurements are recorded in custody's CC-002 task. New exports remain unreleased under the unchanged package version.

| `waitForEvmTransaction(...)` | Read-only `eth_getTransactionReceipt`, `eth_getTransactionByHash`, and `eth_chainId`; policy-dependent `eth_blockNumber` and `eth_getBlockByNumber` | Given the prepared request and sender, verifies the receipt, hash/from/to/input/value/network identity, action-specific privacy event, and explicit finality policy. It fails closed without a policy; depth/`safe`/`finalized` policies recheck the canonical inclusion-block hash. |
| Chain time for relay expiry validation | Caller supplies the latest chain block time | The README latest-block REST helper is an example, not a fixed SDK relayer API |

Privacy scan, circuit, asset, Merkle path, and nullifier queries use the configured Clairveil REST endpoint by default. An EVM chain may inject a complete `PrivacyStateAdapter` to provide the same reads through contract getters or an indexer. Only a runtime EVM profile that receives the adapter in the same constructor call may omit Cosmos `rpc` and `rest`; serialized `BrowserWalletProfile` and `ClairveilWebClientConfig` values remain complete deployment contracts and continue to require both endpoints. Adapter reads use `queryTimeoutMs` and bounded `queryRetry` within the same adapter without silently switching providers. The SDK applies the same typed-scan, circuit, asset, Merkle, and reserve validation behind the adapter boundary. `evmRpc` is used for network identity, receipts, finality, and reorg verification.

## On-chain execution mapping

| Operation | Cosmos type URL | EVM execution | Prepared result | Submitting account |
| --- | --- | --- | --- | --- |
| Deposit | `/clairveil.privacy.v1.MsgDeposit` | `IPrivacy.deposit(...)` | Sign doc or EVM transaction | User wallet |
| Native transfer | `/clairveil.privacy.v1.MsgTransfer` | `IPrivacy.transfer(...)` | Sign doc or EVM transaction | User wallet |
| One-Proof Batch Transfer | `/clairveil.privacy.v1.MsgBatchTransfer` | `IPrivacy.singleProofBatchTransfer(...)` or authorization variant | Cosmos sign doc or EVM transaction | User wallet |
| Direct withdraw | `/clairveil.privacy.v1.MsgWithdraw` | `IPrivacy.withdraw(...)` | Sign doc or EVM transaction | User wallet |
| Relay withdraw | `/clairveil.privacy.v1.MsgWithdraw` | `IPrivacy.withdraw(...)` | Relay payload and optional candidate transaction | Product Relayer |

One-Proof Batch Transfer maps the same frozen payload, proof, and operation evidence to Cosmos and EVM execution artifacts. The EVM path uses the precompile's canonical single-proof selector and exact calldata; it never falls back to multiple independent `transfer` calls.

## Relay and proxy non-fixed contracts

The `/relayer/withdraw` and `/relayer/evm-withdraw` routes in the README are integration examples, not fixed endpoints provided or called by the package. A Product Relayer must define these responsibilities separately:

- Authentication and replay prevention
- Fee, rate-limit, and queue policy
- Authoritative chain-time and expiry validation
- Payload hash, recipient, and chain-ID validation
- Rebuilding the EVM `to`/`data` or Cosmos `MsgWithdraw`
- Returning submission result and transaction identity

The DApp proxy is also a product contract. Even a simple CORS proxy must not collect or log the privacy-root signature, root seed, private scalar, or decrypted notes.

## Boundary between success and state

| Observed value | What it establishes | What it does not establish |
| --- | --- | --- |
| Prepared sign doc / EVM transaction | Proof and transaction artifact are ready | Network submission or success |
| Network `txHash` or Cosmos exact signed `txBytesHash` | A transaction identity exists that can be queried on chain | Chain success or creation of the desired output |
| EVM `txBytesHash` | Local binding between the prepared EVM transaction request and reservation | Network submission, RPC transaction identity, or chain success. A `txHash` returned by `eth_sendTransaction` is still required. |
| Successful tx result / receipt | The transaction executed successfully | That it matches the expected payment/output |
| Input nullifier spent | The input note was consumed | Payment or payroll-item success |
| EVM network `txHash` + prepared `txBytesHash` + successful receipt + verified RPC call/event + verified finality policy + expected output evidence match | The EVM operation can be considered successful | A state where only some linked inputs have been verified |

Direct submission flows that use the Reservation API must record durable `markBroadcastAttempting(...)` evidence immediately before external broadcast, then call `markSubmitted(...)` after submission or `markUnknown(...)` when the result is uncertain. Do not start a local broadcast for a payload that has already crossed an external boundary through `recordRelayHandoff(...)`. A hash returned by a relayer cannot establish `Submitted` by itself; first confirm inclusion of the exact payload through an authoritative chain lookup, then call `recordRelayTransactionEvidence(...)` with the payload hash, network transaction hash, checked height, and literal inclusion evidence. High-level EVM preparation records `execution_transport: "evm"` and the prepared `txBytesHash` at `ProofReady`. `markSubmitted(...)` and `recordRelayTransactionEvidence(...)` require a network `txHash` for that record, while `reconcileSpentNotes(...)` requires both network and artifact hashes plus the successful receipt, RPC transaction identity, privacy-event, and finality verification returned by `waitForEvmTransaction(...)`. A custom low-level EVM path must set the same transport tag through `markProofReady(...)`. The SDK broadcast helper can manage this lifecycle for the caller.
